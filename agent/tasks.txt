EXECUTION RULES

1. Dependency-first execution

Execute tasks strictly in dependency order.

Do not jump directly to UI work when the required domain/database/API behavior does not exist.

Preferred order:

Audit ↓ Existing bugs / integrity problems ↓ Domain model ↓ Database ↓ Backend/domain services ↓ API/RPC ↓ Frontend ↓ Concurrency/security ↓ Tests ↓ Operational automation ↓ Advanced features 

2. Audit before implementation

Before Task 1:

inspect repository structure

inspect database schema

inspect SQL functions

inspect triggers

inspect views

inspect domain repository

inspect API routes

inspect frontend pages/components

inspect authentication/session handling

inspect payment/reservation logic

inspect trip/trajectory/WPoint logic

inspect existing tests

inspect build configuration

Produce an internal implementation map.

Do not rewrite working functionality simply to match your preferred architecture.

3. Existing functionality takes precedence

For every feature:

Already implemented correctly → verify and mark complete. Partially implemented → complete it. Implemented incorrectly → fix it. Not implemented → implement it. 

Never duplicate:

routes

database functions

domain logic

components

state machines

validation logic

payment logic

notification systems

4. Database safety

Never silently change existing business semantics.

Before modifying the schema:

inspect foreign keys

inspect cascades

inspect unique constraints

inspect triggers

inspect functions/procedures

inspect views

inspect indexes

inspect existing API dependencies

Business-critical operations must be atomic.

Where the database transport requires a single SQL statement:

use writable CTEs

avoid multiple independent writes

do not assume cross-call transactions exist

do not pass JavaScript arrays where the transport converts them to JSONB instead of PostgreSQL arrays

5. Server-side enforcement

Never rely exclusively on frontend validation.

Every important rule must be enforced at the backend/database layer.

Examples:

authorization

ownership

seat capacity

payment state

reservation state transitions

trip status transitions

WPoint validity

commune/Wilaya relationships

pricing

cancellation rules

refunds

driver permissions

6. Concurrency

Business-critical operations must remain correct when two requests happen simultaneously.

Explicitly test:

last-seat race

simultaneous reservation

simultaneous driver approval

payment vs hold expiration

cancellation vs payment

trip cancellation vs booking

duplicate payment webhook

duplicate refund request

Use appropriate database locking, atomic statements, constraints, or transactions.

7. State machines

Do not implement business states as scattered ad-hoc conditionals.

Explicitly define legal transitions for:

scheduled → in_progress → completed 

and:

scheduled → cancelled 

with appropriate restrictions.

Reservation

Define and document all states required by the existing application, including:

completed

no_show

waitlisted

Use the existing schema terminology where possible rather than introducing unnecessary aliases.

Payment

Define:

pending

successful/paid

failed

expired

refunded

partially refunded

Only allow legal transitions.

2. Transport quirks you must know before writing any new SQL here

backend/DB/connection.ts supports two transports selected by config:
direct (pg pool, real bound parameters, real transactions via
transaction()) and management-api (Supabase Management API's
/database/query endpoint, which takes a single opaque SQL string with no
server-side bind parameters). In management-api mode, DBHelper.raw(sql,   params) → connection.execute() → apiExecute() calls
inlineParams(sql, params) (in backend/DB/sql-utils.ts), which replaces
$1, $2, … with escaped literals via sqlLiteral(). Consequences
that have already bitten this project and must be remembered:

Only ONE statement per db.raw() call is reliable (execute()'s own
docstring says "Execute a SINGLE SQL statement"). Need multiple
writes to happen together atomically? Use a single statement with
writable CTEs (as setWpointCommunes and reorderWpoints both do), not
multiple db.raw() calls — there is no cross-call transaction in
management-api mode (transaction() throws if not in direct mode).

JS arrays passed as a param become a jsonb literal, not a Postgres
array (sqlLiteral does JSON.stringify + ::jsonb for
arrays/objects). You cannot do commune_id = any($2) with $2 bound to
a JS array under this transport. The established workaround (used twice
now) is to build a VALUES (...), (...), ... list with one $n
placeholder per element, appending to the params array and computing
each placeholder's index off params.length as you go — see
reorderWpoints and setWpointCommunes in domain.ts for the exact
pattern to copy.

Deferrable-immediate unique constraints (e.g.
wpoint_traj_position_uk) are only checked at end-of-statement, which
is what makes single-statement multi-row reorders/replacements safe even
with transient duplicates mid-statement — but this safety only holds
within one statement; splitting the work across multiple db.raw()
calls would reintroduce the risk of hitting the constraint on an
intermediate state.

Error mapping (backend/api/middleware/errors.ts): ApiError thrown
anywhere → its own status/code; ZodError → 400; Postgres 23505
(unique violation) → 409 CONFLICT; Postgres 23503 (FK violation) → 409
IN_USE; anything else (including a plain Error thrown from
domain.ts) → generic 500. The established convention in this codebase
is: domain.ts throws plain Errors; routes decide whether/how to
translate them into a specific ApiError (see the BAD_COMMUNE
string-matching shim in admin.ts/driver.ts as the current — slightly
hacky — example; a cleaner follow-up would be a dedicated typed error
class instead of substring matching, if you ever touch that code).
